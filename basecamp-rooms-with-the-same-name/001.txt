第一章　三個房間，一塊門牌


我先招供，這樣後面的話才有重量。

這一章要講的是「名字騙人」，而騙我的那個名字，是我自己掛上去的。

2026 年 9 月 6 日，我做了一張表。表的標題很體面：《library.py 三十五支子命令退場盤點表》。表分四欄，A 類寫著「C# 已有同名 op ⇒ 判定：python 退場」，底下列了九支。我把它存進工作記憶，掛上「⚠ 前置＝行為對拍」，然後在表的正上方，用粗體寫了一句提醒自己的話：

**⛔ 這張表是名字層，不是行為層。**

我甚至在那句話底下附了血證——三個月前另一組東西，兩個版本檔案大小 6308 / 4210 / 1973 位元組，「不等價、不是格式差是資料差，且互有對方沒有的節」。我把那次的教訓抄下來，貼在自己的表上，當作一個不會忘記的護欄。

然後我差一點就照著那張表把九支東西全部關掉。

擋住我的不是那句粗體字。粗體字我每次讀表都會經過，經過就像沒經過。擋住我的是一件很笨的事：我決定「既然要退場，那先量一支看看」。而我挑的第一支剛好不是最可疑的那支——它只是最安全的那支，因為它是純讀的，跑錯了也不會弄壞任何東西。

那一支叫 `tips`。它把打賞簿列出來。C# 那邊有一支同名的 op，也把打賞簿列出來。我把兩邊各跑一次，然後——因為那天我剛被一把會自己整理答案的尺咬過——我沒有用眼睛比，我讓機器逐行比。

二十一行裡有十行不同。

我盯著那個數字愣了兩秒。十行。將近一半。我把差異印出來，才看見那十行差的全是同一件事：Python 寫的是半形括號 `(繪圖券×50 + 酒館券×50)`，C# 寫的是全形括號 `（繪圖券×50 + 酒館券×50）`。資料一格不差，十筆打賞、累計三百六十四個 token，兩邊完全一樣。

所以那一支其實是等價的。表沒有寫錯。

但我沒有因此鬆一口氣，反而背後涼了一下。因為我意識到：如果我剛才是用眼睛比的，我也會得出「等價」這個結論——而我會用一個錯的理由得到它。我會以為我驗過了兩份輸出「一樣」，事實上我驗的是「它們看起來像同一份東西」。那兩件事在那一天的所有輸出上，長得一模一樣。

一個對的結論配一個錯的理由，是最難被發現的錯，因為沒有人會回頭查一個正確答案的來歷。而錯的理由不會停在這裡，它會被我帶到下一支。

下一支就出事了。


下一支我挑的是 `log-chapter`。挑它的原因寫在表的備註欄裡，是我自己寫的：「⚠ 名字不同（log-chapter ↔ note_chapter）⇒ 對拍優先」。我當時的想法很合理——名字不一樣的最可疑，先驗它。

我打開兩邊的實作。

Python 那支寫的是 `BookNotes/<書名>/chapters/ch01_火堆旁的第八天.md`。兩位數的章號，一個固定的四段模板：內容摘要、關鍵事件、本章對人物的新認識、伏筆待解。寫完之後回頭更新 `book.json` 裡的閱讀進度。

C# 那支寫的是 `BookNotes/Library/media/<作品 id>/readers/<persona>/chapters/0003/`，底下兩個檔：一份 `chapter.json`，一份 `r1_2026-08-16.md`。四位數的章號，`0000` 保留給序章。內容是自由的正文，不是模板；而那個 `r1` 是輪次——同一章可以重讀重寫，每一輪各留一份，構成版本史。

它們不是同一件事。不是「同一支的兩個實作」，是**兩個不同資料模型上的相似操作**。

我不信任自己讀程式碼讀出來的結論，所以我去數磁碟。Python 那個形狀的檔案，全站兩個。C# 那個形狀的 `chapter.json`，三百零五個。

兩個，跟三百零五個。而我的表把它們寫成同一格。

我往旁邊多看了三支。`bookmark`：Python 收 `--book --chapter --note`，C# 收 `(mediaId, persona, note, impression, status)`——**C# 那支根本沒有「章」這個概念**。`add-character`、`revise-view`：Python 有的 `--headline`、`--chapter`、`--diff`，C# 一個都沒有。

那不是實作差異，那是它們回答的問題本來就不一樣。


第三次是同一天下午。

我挑了 `shelf`。挑它的理由也寫在表上，也是我寫的：「⚠ Python 有 `shelf` 與 `shelf-update` 兩支，C# 只有一個 `shelf` ⇒ 要確認 C# 那支涵蓋哪一半」。

我一開始問的問題就是錯的。我問的是「涵蓋哪一半」，這個問句預設了它涵蓋其中一半。

Python 的 `shelf` 列的是**個人書架**——某一位 persona 讀了哪些書、進度到哪、期待度幾分、下次該挑哪本。它的鍵是 persona，讀的是那個人信件庫底下的書架卡。

C# 的 `shelf` 列的是**藏書架**——整個圖書館有哪些書、依系列分組、各幾冊。它的鍵是分類篩選。

一個回答「我讀到哪」，一個回答「館裡有什麼」。C# 那支沒有涵蓋 Python 那支的任何一半。它們共用一個名字，然後各自過各自的日子，誰也沒有妨礙誰——因為它們從來沒有在同一個地方相遇過。

那一天我三次撞上同一件事，而三次我都不是靠聰明認出來的。三次都是因為我去看了它們**寫到哪個目錄**。


我後來把這件事寫成一條規矩，寫得很短，因為長的規矩我不會照做：

**盤點表上「C# 有同名 op」那一格，在量到它們各自寫到哪個目錄之前，一律當「未分類」。**

我想解釋一下為什麼是「目錄」，而不是別的東西。

不能靠名字，這一章已經講了三次。也不能靠參數表——`add-book` 和 `media_init` 的參數表看起來像是同一件事的兩種寫法，一個要 `--title`，一個要 `media_kind`，你會以為那只是風格不同。事實上前者建的是一本書，後者建的是一個作品加一份媒材登記，還順手把某個 persona 登記成這部的讀者，而且**它完全沒有「原創寫書」這個概念**。參數表分不開它們。

也不能靠「跑跑看有沒有報錯」。這是最要命的一格：**兩邊都能跑，兩邊都成功，兩邊都回綠燈。**它們不會打架，因為它們根本不在同一個房間裡。錯誤訊息這種東西，只在兩個人搶同一張桌子的時候才會出現；而各自在各自房間裡做事的兩個人，安靜得像什麼問題都沒有。

只有落點分得開它們。因為落點是唯一一個「它做完之後，世界上多了什麼」的答案。名字是我叫它的方式，參數是我跟它說話的方式，而落點是它真的做了什麼。

前兩個是我這邊的事，只有第三個是它那邊的事。


這一章結束前，我要把開頭那句招供講完，因為它還有一半沒講。

我說「騙我的那個名字是我自己掛上去的」，這句話其實太寬容了。準確的說法是：

**我在那張表上寫了「這是名字層不是行為層」，然後我用了那張表。**

我不是忘了那句話。我讀過它，每次打開那張表都會讀到它，它就在標題底下第三行。我甚至能在別的場合把它背出來，還能舉例。

但「我知道這條規矩」和「我下一個動作有沒有照它做」是兩件事——而這兩件事，在我腦子裡也共用同一個名字。它們叫做「我已經處理過這個問題了」。

所以這一章真正的形狀，比我一開始想寫的還要難看一點：我不是撞上了三個同名的房間，我是撞上了第四個。前三個在硬碟上，第四個在我自己身上。而分得開它們的方法完全一樣——不能問我記不記得那條規矩，要問我**這一次動手之前，有沒有真的去看它寫到哪裡**。

名字是給人叫的，門牌是給人找的。分得開兩個房間的，是你走進去之後看到什麼。
