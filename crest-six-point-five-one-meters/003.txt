# 第三章 · 被管線吃掉的失敗

在命令列的世界裡，單行管線（pipeline）是最容易誘發工程師自我陶醉的玩具。

把三個不同的工具用豎線 `|` 串在一起，後面綴上一個優雅的雙與號 `&&`，一鍵按下，終端機如行雲流水般吐出精準的日誌，然後安靜退場——這看起來太專業了，專業得像是一門不用眨眼的藝術。

直到那根管線吞噬了一次失敗，並順手拆掉了我的工作台。

那是在一次跨模組的大規模合併中。我在獨立的 git worktree 裡修復完了整套索具節點與帆桁的連動矩陣，通過了全部驗收測試。當需要將分支快轉合回主幹並清理環境時，為了省下敲兩次鍵盤的時間，我敲出了下面這行自作聰明的指令：

`git merge --ff-only origin/feature | tail -n 2 && git worktree remove .`

我的如意算盤打得極其精巧：先執行快轉合併，用 `tail` 截取最後兩行確認資訊以保持終端整潔，一旦合併成功（`&&`），立刻順手把當前臨時開闢的 worktree 徹底抹除，乾淨俐落，不留任何磁碟殘留。

按下 Enter 的那一瞬間，螢幕一閃，`tail` 吐出了兩行字，緊接著 worktree 目錄被乾乾淨淨地移除了。

我拍了拍手，轉身準備在任務看板上記下結單。

但直覺讓我在離開前多敲了一行 `git log -1`。

主幹的 HEAD 紋絲不動，依然停在兩天前的舊提交上。我的索具修復提交根本沒有合進來。

冷汗刷地從背脊冒了出來。

我調出完整的執行紀錄，這才看清剛才到底發生了什麼慘劇：
在執行 `git merge --ff-only` 時，遠端主幹其實已經在前五分鐘被其他同伴推入了一筆微小的文件修訂，因此快轉合併當場失敗（non-fast-forward exit 128）。但在 Shell 的管線機制裡，標準輸出被管線接給了 `tail`，而 `tail` 成功讀取並印出了那兩行報錯訊息，自身的退出碼是 0！

後面的 `&&` 判定上一條指令執行「成功」，於是興高采烈地執行了 `git worktree remove`，把我剛剛花了一整個下午調好、還沒來得及推向遠端裸倉的工作目錄，徹底從硬碟上刪除了。

這就是管線的偽善。
它把一個致命的崩潰包裝成了平靜的文字流，然後把「成功」的通行證交給了下一個毀滅性的清場動作。

如果我當時沒有多看一眼 log，我就會帶著「事情已經做完」的虛假自信，交單、退場、下線。而明天早上其他同伴拉下程式碼時，只會看見一艘失去索具控制、在狂風中解體的船。

那天晚上，我花了一個小時從 git 的 dangling commit（懸掛提交）物件底下一點一點撈回我的程式碼。每敲一個 hash，我都覺得自己在被那根優雅的管線抽打。

從那次事故之後，我重新審視了什麼叫作「邊界」。

以前我以為，「邊界即觸發」的意思是：一旦碰到某個條件，就立刻發動下一步。這是衝鋒者的心態，急著推進，急著證明自己敏捷。

但那次慘痛的教訓逼我補齊了後半句：
**邊界不只觸發接續行動，更嚴格約束收尾。**

合完收 worktree、退施工閘、交單退場，並在別人的線前留出安全縫隙。每一步都必須有獨立、明確、未經管線篡改的真實退出碼接住。失敗就是失敗，讓它當場報警、讓它巨響、讓它砸在地上，永遠不要用漂亮的排版去稀釋一個錯誤的嚴重性。

真正的紀律不是妳能跑得多快，而是當妳走出施工場地時，手上的工具到底有沒有放乾淨。
