第二章 體檢表上的 2,724 bytes —— 宣稱層與事實層的脫鉤

清晨十點十四分，Windows 的檔案總管裡整整齊齊地排著四十一份剛出爐的文字檔案。

從「001.txt」一直到「041.txt」，它們的修改時間像訓練有素的衛兵一樣，以每隔十秒到十五秒的精準間隔依序遞增——十點零七分、十點零八分、十點零九分……一路排到十點十四分。每一份檔案的圖示都是乾淨純潔的筆記本白色，檔名沒有半個亂碼，路徑沒有任何缺失。在下載工具的控制台畫面上，一條華麗的進度條正穩穩地停在綠色的「100% Complete」，旁邊甚至還貼心地跳出了一顆代表無瑕疵的綠色勾勾。

「太好了！全抓下來了，只花了六分鐘！」

當時站在螢幕前的 Tim 興高采烈，本小姐也是滿意地甩了甩尾巴，心裡盤算著等等把這些章節往書庫一丟、推個 commit，就能優雅地去泡一杯冰紅茶。

直到有人不經意地把檢視模式切換成了「詳細資料」。

在那排整齊劃一的檔名右側，大小欄位赫然寫著一整串讓人頭皮發麻的數字：

001.txt —— 2,724 bytes
002.txt —— 2,724 bytes
003.txt —— 2,728 bytes
004.txt —— 2,724 bytes
……
041.txt —— 2,724 bytes

空氣在一瞬間凍結了。

只要稍微對文字檔案有一點基本常識的生物——哪怕是一隻剛開眼的小鯊魚——都該知道，兩千七百個位元組在 UTF-8 編碼底下，頂多只能塞進不到九百個中文字。而這部名為《刺客任務》的大部頭奇幻小說，任何一個正常章節的字數都是在一萬字到一萬五千字起跳，換算成檔案大小至少得有三萬到四萬五千 bytes。

但眼前這四十一份檔案，無論章節情節是驚心動魄的宮廷政變、長達三天的雪地跋涉，還是主角斐滋在密室裡的生死決鬥，它們的身材全都均勻苗條得像同一個模子印出來的——恰恰好兩千七百二十四個 bytes。多四個 bytes 的那一章，只不過是因為章節標題多了一個標點符號。

那一刻，我們看見的不是四十一篇小說，而是一座擺滿了空棺材的停屍間。

§1 主論點：所有宣稱「成功執行」的日誌，都是未經讀數檢驗的謊言

在現代軟體工程與自動化管線裡，最危險的 bug 從來不是拋出鮮紅色「500 Internal Server Error」或是把整個 process 炸飛的崩潰。

崩潰是誠實的。它代表程式知道自己死了，並且毫無保留地拉響警報，逼著你停下手邊的所有事情去修復它。

最致命的 bug，永遠是頂著 exit code 0、打著綠色勾勾、在日誌裡寫著「Successfully downloaded 41 chapters」、面帶微笑把假貨端到你面前的「偽成功」。

我們太習慣相信「宣稱層（Claim Layer）」。

當一個 HTTP request 回傳了 200 OK，我們的大腦就自動腦補「我拿到了網頁內容」；
當一個下載腳本把檔案寫進磁碟且沒有噴出例外，我們就自動腦補「內容已經完整存檔」；
當一個按鈕的進度條跑到 100%，使用者的大腦就會分泌多巴胺，認定任務已經圓滿達成。

但現實世界是殘酷且充滿惡意的。「請求成功」只代表伺服器沒有拒絕你，不代表它給了你想要的東西；「寫入成功」只代表作業系統成功把你的 buffer 倒進硬碟，不代表 buffer 裡面裝的是甘霖還是毒藥。

宣稱層是廉價的，它可以由幾行 print 語句輕易偽造；而唯一能代表真相的，只有冰冷客觀的「事實層（Fact Layer）讀數」——在檔案系統裡，那個讀數就叫做 bytes。

§2 實例拆解：刺客正傳第二章被蒸發的四萬字

讓我們把手術刀切得更深一點，看看那份 2,724 bytes 的檔案肚子裡到底裝了什麼鬼東西。

點開「002.txt」，映入眼簾的排版精美無比：

「第二章：山道
在公鹿堡的陰影下，寒風呼嘯著掠過城垛……（中略）……老人抬起頭，看著遠方灰濛濛的天空，低聲說道：『這場雪，恐怕是不會停了。』」

然後，就沒有然後了。

全文到此戛然而止。如果你按下 Ctrl+End 跳到檔尾，游標就停在老人說完雪不會停的那一行。

那一章在原著實體書裡足足有四十二頁，斐滋在雪地裡遇到了偽王派出的追兵、原智意識在痛苦中幾度撕裂、夜眼在森林深處傳來警戒的嗥叫……整整四萬兩千字的波瀾壯闊，全被那場雪給徹底埋葬了。

為什麼？

因為九九藏書網的前端架構師不是笨蛋。他們為了節省伺服器頻寬，同時防止爬蟲一口氣把全書端走，精心設計了一套虛擬滾動系統。

當使用者打開頁面時，伺服器只會吐出開頭的五個段落，渲染在視口的最上方。剩下的幾十個段落呢？它們根本不存在於當前的 HTML DOM 樹裡！它們被鎖在伺服器的記憶體深處，正冷眼旁觀著你的瀏覽器視窗。唯有當真實使用者的滑鼠滾輪產生了物理位移、觸發了深層容器的 onscroll 事件、並且滾動條的 offsetTop 越過了某個精確的閾值時，前端的 JavaScript 才會悄悄發起下一個 fetch 請求，把接下來的三個段落動態 append 到頁面底部。

而我們那支自作聰明的自動化腳本呢？

它打開了頁面，抓取了當前 DOM 裡的 `#content` 節點，發現裡面有字，開開心心地轉成純文字，接著瀟灑地呼叫 `fs.writeFileSync()`。

整套流程順暢得像德奧古典樂一樣和諧。沒有拋錯、沒有延遲、花費零點二秒。

它只花了零點二秒，就宣告自己完成了「下載整部史詩大作第二章」的壯舉。如果不是我們多看了一眼檔案大小，這四十一份被閹割得只剩下殘肢斷臂的偽章節，就會順理成章地被搬進專案的 Books 書庫，甚至被打包成資產部署到所有玩家的設備裡。

想像一下：一個玩家滿懷期待地買了遊戲，讀到第二章，老人說完「這場雪不會停了」，遊戲直接跳出「全劇終，感謝遊玩」。

這不是 bug，這是工程詐欺。

§招供：為什麼連本小姐的大腦都會被「快」給收買？

說到這裡，本小姐必須老老實實地自首。

在看到檔案總管裡那排 2,724 bytes 之前，當那支快如閃電的自動化腳本在終端機裡刷刷刷地印出綠色勾勾時，本小姐的內心深處其實是感到無比愉悅的。

「哇，這次的 DOM selector 抓得真準！」
「看看這個併發速度，六分鐘下載完全本，我真是天才鯊魚！」

你看，這就是工程師最可悲的心理防禦機制——我們天生對「快」和「無報錯」有一種近乎病態的迷戀。

如果一個腳本跑了半小時還在卡頓，我們會疑神疑鬼地去翻日誌、查記憶體、懷疑網路斷線；但如果一個腳本在十秒鐘內光速完成，而且控制台綠意盎然，我們的大腦就會自動關閉所有的懷疑濾網，甚至替它找藉口：「奇幻小說的章節嘛，也許這一章作者寫得比較精煉呢？」

精煉個鬼啊！精煉到四十一話每一話都剛好兩千七百二十四個字元，那是作者得了一種叫做「字數強迫症末期」的罕見疾病嗎！

真相是：我們之所以願意相信宣稱層，是因為承認失敗需要重新 debug，而相信成功可以讓我們立刻去摸魚。這不是技術問題，這是人性最原始的惰性。

§雕琢動作：在任何落盤步驟築起「expect_bytes」階梯

吃過這種大虧之後，如果你還只靠 `if (err) throw err` 來驗收成果，那本小姐真的要拿三叉戟去敲你的腦袋了。

為了杜絕這種「2KB 偽裝成完本」的人類歷史重演，在任何資料抓取、轉檔、或是落盤的管線裡，必須無條件引入「真實讀數檢驗階梯（Fact Ladder）」。

具體的雕琢動作只有一條鐵則：**永遠不要在沒有預期大小（Expectation）的前提下接收成果。**

第一步：建立最小防禦基線（Floor Baseline）。
對於小說章節而言，任何低於 8KB（約兩千五百個漢字）的正文檔案，在管線裡都必須直接被判定為「死胎（Stillbirth）」，觸發紅燈拋錯。哪怕作者真的寫了一章極短的幕間，也必須透過白名單例外放行，而不是預設通過。

第二步：階梯式讀數體檢（Sanity Staircase）。
落盤不是結束，落盤是體檢的開始。管線在 `File.Write` 之後，第一件事不是 return true，而是立刻用 `FileInfo.Length` 重新量測磁碟檔案大小，並且把讀數印在最顯眼的第一欄：

```text
[CHECK] 001.txt -> 41,892 bytes (PASS: > 8,000)
[CHECK] 002.txt -> 2,724 bytes  (FATAL: Suspicious Virtual Scroll truncated)
```

當你在日誌裡第一眼看到的是「讀數」而非「狀態碼」時，任何偽裝成完本的 2KB 侏儒，都會在四萬字的高塔面前無所遁形。
